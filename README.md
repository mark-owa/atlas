# Atlas — Business Operations Demo

**Portfolio role:** an earlier, intentionally compact prototype for exploring process mining and guarded workflow execution.

Atlas is a compact Python prototype that reconstructs lead-processing journeys from
sample events, summarizes manual work, and executes a fixed lead-routing workflow.
It demonstrates process mining, graph validation, persisted workflow state, human
approval, and assumption-based ROI calculations.

**Portfolio note:** Atlas predates this public repository. It was added later as a small example of earlier workflow-design work, so its GitHub history begins at publication.

## Run locally

Requires Python 3.10 or later; verified with Python 3.12. From this directory:

```bash
python -m venv .venv
# Linux/macOS:
source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m uvicorn atlas:app --reload
```

Open <http://localhost:8000>. Choose **Setup Demo Data**, then **Deploy**.
**Low-risk** assigns a simulated CRM lead. **High-risk** pauses for **Approve** or
**Reject**; rejection records a simulated notification without assigning the lead.
The page displays the current execution and its step history.

Setup **resets all existing data for the demo organization**, then creates 100
journeys containing 300 events. Authentication and setup are open development
endpoints: run this demo locally, not as a public service.

Interactive API documentation: <http://localhost:8000/docs>. To call protected
endpoints there, obtain an `access_token` from `POST /api/auth/login` and put
`Bearer <token>` in the endpoint's `authorization` header field. ROI is exposed
through `POST /api/automations/{opp_id}/roi`, with this example body:

```json
{
  "hourly_labor_cost": 50,
  "automation_runs_per_month": 100,
  "implementation_cost": 1000,
  "api_cost_per_run": 0.02,
  "avg_human_action_minutes": 5
}
```

Use one currency consistently for all cost inputs. Values are estimates, not
measured business savings.

## Behavior and design

- **Mining:** groups events by organization and entity, orders them by timestamp
  and ID, and reconstructs journeys containing at least two events. Repeated
  event types flag a journey as anomalous; this is a simple heuristic.
- **Interpretation:** selects the process with the most total human events.
  Optional OpenAI text uses those summary facts. The workflow is a fixed template,
  not generated by AI. Classification is a case-insensitive `spam` substring check.
- **Validation:** Pydantic restricts step types and actions. Graph validation rejects
  duplicate IDs, missing targets, unreachable steps, and cycles. It never runs
  arbitrary Python or shell code.
- **Execution:** runs synchronously and stores context, current step, action results,
  and history in SQLite. Each successful step commits its database action, history,
  and next-step pointer together. A recoverable action failure rolls back that step
  and records failure; earlier completed steps remain committed.
- **Approval:** persists the pause, then records the token's user identity and the
  decision before continuing. Approved and rejected approval history is completed.
  A second decision on an already finished execution is rejected.
- **CRM:** assignment creates or updates one lead per organization/entity. Repeated
  execution updates the same row but creates a new execution; requests are not
  deduplicated. Notifications only record a simulated result, with no delivery.
- **ROI:** compares mined manual-step counts with completed executions. The provided
  workflow has at most one approval per run; each approval is estimated as one
  `avg_human_action_minutes` action. Execution duration accumulates processing time
  across resumes and excludes human waiting time. With no completed executions,
  the projection assumes zero approvals; it is not evidence of zero human effort.
  No positive savings means no payback estimate; zero implementation cost returns
  `roi_percentage: 0` as a convention, not a meaningful percentage return.

## Configuration

Environment variables are read at import/startup; `.env` files are not loaded.

| Variable | Default / meaning |
| --- | --- |
| `DATABASE_URL` | `sqlite:///./atlas.db`, relative to the working directory. Tables are created at import. |
| `APP_ENV` | `development`; other values disable demo login and setup. |
| `JWT_SECRET` | Public development placeholder. Outside development, startup requires a different secret of at least 32 bytes. |
| `CORS_ORIGINS` | `http://localhost:8000`; comma-separated allowed browser origins. |
| `OPENAI_API_KEY` | Empty: deterministic interpretation. If set, aggregate process facts are sent to OpenAI using `gpt-4o`; charges may apply. API errors or invalid replies fall back to deterministic text. |

Tokens expire after 30 minutes. Refreshing the page obtains a new demo token but
also clears its current selection; saved execution history remains accessible by
ID through the API. Do not select setup when you want to retain previous runs.

## Tests

```bash
python -m pytest -q
```

Tests use a separate temporary SQLite database and force development mode with
AI calls disabled. They do not reset your configured application database.
The suite covers routing, approval/rejection, tenant filters, graph validation,
repeated assignment, ROI, database rollback, startup checks, and mocked AI failures.

The repository contains `atlas.py` (models, services, API, and embedded demo page),
`test_atlas.py`, dependency versions, and this README. The single-file structure is
intentional for the current scope.

## Limitations

- This is a local prototype, not production-ready software. There is no
  password login, user provisioning, role management, or real CRM/notification
  integration. Disabling development mode does not supply replacement identity
  management.
- Execution has no worker queue, automatic retry, concurrency protection, or crash
  recovery. A process interruption can leave a run marked `running`. An already
  saved approval pause can be resumed by ID after restarting.
- SQLite is the verified database. There are no schema migrations; changing models
  does not migrate an existing database. Persistent database outages can prevent
  even failure history from being saved.
- Mining loads the organization's events into memory. There is no event-ingestion
  API, pagination, or large-volume performance claim. One entity is treated as one
  journey; the recommendation template remains lead-specific for other processes.
- Optional AI wording is not independently fact-checked. Live OpenAI calls were
  not verified; tests mock their failure paths. The demo page uses Tailwind's CDN
  for styling, so styling needs internet access.
- ROI excludes failed/pending executions and assumes the supplied one-approval
  workflow. It does not establish causation, actual labor time saved, or realized ROI.
